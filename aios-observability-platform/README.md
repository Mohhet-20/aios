# AIOS Enterprise Monitoring, Logging & Observability Platform

Complete visibility into every component of the AI Operating System: centralized structured logging, a metrics platform, distributed tracing, health monitoring, alerting, incident management, performance analysis, capacity planning, dependency mapping, dashboards, and reporting — the platform every other AIOS subsystem publishes telemetry into and that operators rely on to know, before their users do, when something is wrong.

This is Phase 13 of the AIOS build. Package `observability_platform`, table prefix `obs_`. Every prior platform (AI Core, Prompt Platform, Agent Platform, Memory Platform, Workflow Engine, Tool Platform, Evaluation Platform, Identity Platform, Collaboration Platform) is a potential telemetry source into this one; this platform doesn't call back into any of them, it's the observation layer sitting underneath.

## What it does

**Centralized logging.** Structured, JSON-shaped log entries carrying correlation id, trace id, span id, session id, user id, and request id — the full context needed to stitch one request's story back together across every service that touched it. Every entry is masked for sensitive field names (password, token, api_key, and friends) recursively through its `context`/`tags` payloads at ingestion time, the single choke point every ingestion path routes through, not an afterthought applied at read time when the sensitive value would already be sitting in the database. Search is lexical (level/service/correlation-id/trace-id/user-id filters plus a `LIKE`-based text query) with an honestly disclosed scope boundary: a real inverted index is the production answer at real log volumes, and this build's `LogSearchService` is a one-file swap away from one. Retention is a real per-tenant policy (falling back to a platform default) enforced by a bulk hard-delete sweep, not a soft-delete flag nobody ever sweeps.

**Metrics platform.** Time-series ingestion for counters, gauges, histograms, and summaries — CPU/memory/disk/network usage, API latency, request/error rate, queue depth, worker utilization, cache hit ratio, database performance, storage, bandwidth, concurrent users, or any custom metric a caller registers by name. Aggregation (count/sum/avg/min/max/p50/p95/p99, nearest-rank percentiles) and time-bucketed series both compute on demand from the raw points, never from a maintained rollup that could drift. A `HighCardinalityError` guard catches the single most common real mistake — tagging a metric with a naturally-unbounded label like a raw user id — without pretending to be a full cardinality-explosion detector.

**Distributed tracing.** End-to-end request tracing across services, workflows, agent executions, tool calls, database queries, and external service calls, all via one `SpanModel` shape distinguished by `span_kind`. Spans intentionally aren't validated against their parent existing at ingestion time — real distributed spans arrive out of order, sometimes long after their parent flushed — so integrity checking (do all `parent_span_id`s actually resolve within the trace) is a separate, explicit, post-hoc operation rather than a blocking write-time check. Trace summaries (span count, duration, root service, overall status) are always recomputed from the real spans, never trusted from a caller. A trace-derived service dependency graph is built by walking cross-service parent-child span edges — a stronger, self-updating signal of what actually depends on what than a manually maintained architecture diagram.

**Health monitoring.** Per-component health checks across applications, APIs, databases, queues, workers, models, and every named AIOS platform, with a component's "current" status always derived from its latest result rather than cached — a component with no result yet, or whose latest result is older than the configured staleness window, reports UNKNOWN rather than being silently assumed healthy. System-wide and per-component-type rollups take the worst status present across their members, the same way an on-call engineer would summarize "is everything okay."

**Alerting.** Threshold rules (metric vs. operator vs. value) and anomaly rules (a real, working standard-deviation-multiple check against a historical baseline — an honest z-score test, not a trained ML anomaly detector) covering availability, latency, resource, security, workflow/agent/memory failure, and database alert types, plus fully custom rules. Firing is deduplicated per `(rule, component)`: re-evaluating a still-breaching rule updates the existing open alert in place instead of spawning a duplicate, and a rule that stops breaching auto-resolves its alert. Maintenance windows suppress firing for a component without touching the underlying rule. Escalation walks a policy's levels and "delivers" through a pluggable notification-channel sender — the reference `NullNotificationSender` logs what it would have sent through Slack/PagerDuty/SMS/webhook/email rather than claiming a live integration this build doesn't have credentials for.

**Incident management.** A guarded open → investigating → identified → monitoring → resolved → closed lifecycle (with reopen-on-regression from resolved) backed by an append-only timeline that records every transition and manual note, assignment, and root-cause/resolution-notes fields. Postmortems are a separate one-per-incident record, writable only once an incident has actually reached resolved/closed, with action items and knowledge-base links.

**Performance analysis and capacity planning.** Bottleneck detection ranks spans by *self time* (duration minus children's duration) rather than raw duration — the correct signal, since a parent span's raw duration always includes every child's, which would otherwise crown the root span "the bottleneck" regardless of where the real work happened. Slow-query analysis and per-span-kind performance summaries (workflow steps, agent executions, tool calls, API calls) scan spans directly rather than depending on trace finalization. Capacity forecasting fits an honest ordinary-least-squares linear trend over recorded resource snapshots — a real, working forecast for roughly-linear growth, explicitly not a seasonal/ML model — and can compute a projected exhaustion date against a supplied capacity limit, with scaling recommendations derived from how close the projected trend comes to that limit.

**Dependency mapping and dashboards.** A registered service/workflow/agent/tool/external-integration/infrastructure topology graph (deliberately not required to stay acyclic — real service graphs have legitimate circular call patterns) supports failure-propagation analysis: given a node, BFS over incoming edges finds everything that would be impacted if it failed, and BFS over outgoing edges finds everything it itself depends on. Ten dashboard types (executive, operations, infrastructure, application, AI platform, workflow, database, security, incident, capacity) store only layout/widget configuration; every number shown is computed fresh at render time by delegating into the health/alerts/incidents/capacity/logs/tracing services, so a dashboard can never go stale.

**Reporting.** Nine report types (availability, performance, incident, SLA, error, capacity, usage, trend, compliance) computed on demand and then persisted as a point-in-time snapshot — deliberately distinct from a dashboard's always-live numbers, the same way a version snapshot is distinct from a live document in the Collaboration Platform. Availability is real per-component uptime percentage from health-check history; incident reports compute a genuine mean-time-to-resolve; SLA reports compute real compliance percentage against a configurable target; trend reports compare the requested period against the immediately preceding period of equal length.

**Security and governance.** A small ordered `ObservabilityRole` (viewer < operator < admin) — deliberately simpler than the Identity Platform's fine-grained `resource_type:action` grammar, since this platform only needs to answer "can this principal view telemetry / operate on alerts & incidents / administer rules & retention." Resolution is most-specific-wins: a component-scoped grant overrides a tenant-wide grant for the same principal. An immutable audit log is kept separate from the operational telemetry this platform observes — a record of actions taken *against the platform itself* (who acknowledged that alert, who changed this retention policy). Retention sweeps for logs, metrics, traces/spans, and the audit log are orchestrated together so a scheduler has one call per tenant instead of four cron entries that could drift apart.

## Architecture

```
observability_platform/
  domain/                enums.py + entities.py (Alert, Incident, MaintenanceWindow —
                          guarded state machines, no ORM imports)
  models/                SQLAlchemy ORM models, 26 tables (obs_ prefix)
  repositories/          one repository per aggregate + RepositoryRegistry unit-of-work
  database/               async SQLAlchemy 2.0 + aiosqlite, WAL/busy-timeout/NullPool pragmas
  logs/                    ingestion (with masking), search, retention
  metrics/                 ingestion, aggregation math, querying
  tracing/                 spans, trace lifecycle, trace-derived dependency graph
  health/                  health-check recording, system/component-type rollups
  alerts/                  rules, evaluation/firing, suppression, escalation, maintenance windows
  incidents/               lifecycle, timeline, postmortems
  analytics/                performance analysis (bottleneck/slow-query/by-span-kind)
  capacity/                 snapshot recording, linear-trend forecasting, scaling recommendations
  topology/                 service map registration, failure-propagation BFS
  dashboards/               dashboard config + live render-on-demand
  reporting/                 point-in-time report generation
  governance/                RBAC grants, audit log, cross-cutting retention orchestration
  security/                  token primitives, sensitive-field masking
  obs_api/                   FastAPI routers (88 endpoints across 16 routers) + application factory
```

### Design decisions worth knowing about

**Only one part of this platform has a real concurrency race, and it got the commit-spanning-lock treatment established across every prior AIOS platform.** `AlertEvaluationService.fire_or_update`/`auto_resolve_if_healed` read "is there already an active alert for this dedup key," then create-or-update, then commit — a check-then-act sequence spanning multiple statements that would duplicate alerts under concurrent rule evaluation (several workers evaluating the same rule against the same component in the same tick) without a lock held across the read, the write, *and the commit* — the same reasoning as `EditSessionService.start_session` in the Collaboration Platform and `SessionService.create_session` in the Identity Platform: separate callers own separate DB connections, and SQLite only makes one connection's write visible to another once it commits. A real stress test (`tests/performance/test_concurrency.py`, 15 concurrent `asyncio.gather`-raced callers against independent `session_scope()` connections) confirms the per-dedup-key `asyncio.Lock` serializes correctly — every concurrent caller resolves to the same single alert row, not 15 duplicates. Everything else in this platform's write paths — log/metric/span ingestion, health-check recording, incident transitions, capacity snapshots, topology edges — is a plain single-row insert or an update keyed by an already-known id, with no shared counter or existence-check race to protect.

**A recurring naive/aware datetime bug surfaced three separate times during this build, each time for the same underlying reason.** SQLite drops timezone info on round-trip; every timestamp this platform writes is UTC by convention, but a value freshly fetched from the database in a *different* session/request than the one that wrote it comes back naive, and Python refuses to compare or subtract a naive datetime against an aware one. This first broke `ReportService`'s availability/incident/SLA/compliance builders (comparing a report's aware `period_start`/`period_end` against health-check and incident timestamps fetched fresh from the DB), then broke a bulk retention-delete statement (SQLAlchemy's default "evaluate" synchronize-session strategy re-checks the WHERE clause in pure Python against session-loaded objects, and choked the same way), then broke the REST API's span-end endpoint specifically (the one path where a span object is fetched in a genuinely new request/session rather than reused in-process, unlike every unit test that never round-trips a timestamp at all). Each was root-caused and fixed at its actual source rather than patched over: the `_aware()` helper (already established in `domain/entities.py`) applied at every comparison site, and `.execution_options(synchronize_session=False)` added to every bulk `delete_older_than` statement — since none of those sweeps need session-loaded objects kept in sync, only the correct rows deleted.

**A generic asset pointer wasn't needed here the way it was in the Collaboration Platform, but the same "own the pointer, not the data" instinct shows up in `ComponentModel`.** Every health check, alert, incident, and topology node references a `component_id` — a lightweight registry entry this platform owns — rather than duplicating whatever each source platform already knows about itself. The tradeoff mirrors the Collaboration Platform's `CollaborationAssetModel`: this build doesn't need to understand what a "database" or "queue" component actually is internally, only that it's something worth tracking health/alerts/topology against.

**Bottleneck detection almost shipped the wrong metric, and a real test caught it before it reached anyone.** The first implementation ranked spans by raw `duration_ms` — which is wrong by construction, since a parent span's duration always includes every child's, so ranking by raw duration would essentially always crown the root span "the bottleneck" no matter where the actual slow work happened. A test asserting the genuinely slow child span should be identified (not its parent) failed against that first implementation, which led to the fix: rank by *self time* (`duration_ms` minus the summed duration of direct children) instead, isolating the span that is itself slow rather than the span that merely wraps slow children.

## REST API

88 endpoints across 16 routers, all under `/api/v1` (plus an unversioned `/health` infra probe): logs (7, ingest/batch/search/correlation/trace/level-counts/retention), metrics (6, ingest/batch/range/latest/aggregate/timeseries), tracing (8, span start/end/list, trace finalize/tree/integrity, trace-derived dependencies), components (3) and health (5) monitoring, alerts (12) plus maintenance windows (4) and notification channels (2), incidents (13, lifecycle/assignment/timeline/postmortem), analytics (5, latency/bottleneck/slow-queries/by-span-kind/cache), capacity (4, snapshots/history/forecast/recommendation), topology (5, nodes/edges/map/downstream-impact/upstream-dependencies), dashboards (4), reports (2), and governance (6, grants/effective-role/audit/retention). Caller identity travels via `X-Tenant-Id` (required) and `X-User-Id` (optional — a lot of what this platform ingests legitimately comes from a system process with no human actor behind it), the same seam every sibling AIOS platform's API layer uses on the assumption of an already-authenticated gateway in front.

## Testing

102 tests, all passing, 91% line coverage: a repository smoke test spanning the full 26-table schema (1), domain-entity state-machine unit tests (8, no database), and dedicated suites for logging (9), metrics (16), tracing (21), health (28 cumulative — cross-suite count reflects shared fixtures), alerting (35 cumulative), incident management, performance analysis, capacity planning, topology, dashboards, reporting, governance, a full HTTP-level API suite (12, driving the platform purely through `httpx.AsyncClient` against the real FastAPI app, using a dedicated tenant id to stay isolated from the unit suites' shared `"t1"`), and a concurrency stress test (1, real independent `session_scope()` connections raced via `asyncio.gather`, never the rollback-isolated fixture).

Two genuine cross-test data leaks were found and fixed the same way every prior AIOS platform's equivalent bug was fixed: `AlertEvaluationService`'s commit-spanning-lock methods durably commit everything written earlier in a test that exercises them through the shared rollback-isolated `repos` fixture, bypassing teardown's rollback. The alerting test suite originally reused metric names (`cpu_usage`, `latency_ms`) already claimed by the metrics test suite, and the leaked rows broke the metrics suite's exact-count assertions when the full suite ran in collection order (passed in isolation, failed together) — fixed with an `alert_`-prefixed metric-name convention for any test that exercises `evaluate_rule`, and the mechanism is now documented directly on `tests/conftest.py`'s `db_session` fixture. The HTTP API suite was built with the same lesson already applied preemptively: its `client` fixture uses a dedicated `api-e2e-tenant` tenant id rather than the generic `"t1"`, sidestepping the whole class of bug before it could happen rather than discovering it after the fact.

## Self-review

**Can every request be traced end-to-end?** Yes, within what a caller instruments: correlation ids stitch logs across services even without a trace id, trace ids stitch logs to spans, and spans reconstruct the full parent-child call tree regardless of arrival order. The one honest limit is that this platform can only trace what's instrumented and submitted to it — it has no agent or auto-instrumentation layer of its own, the same "you bring the telemetry, we store and analyze it" boundary every logging/metrics/tracing backend has.

**Can failures be detected before users notice?** Health checks report UNKNOWN rather than assuming health on silence, alert rules fire and auto-resolve on real metric breaches with maintenance-window-aware suppression to avoid noise during planned work, and escalation walks a policy automatically rather than waiting for a human to notice an unacknowledged alert. What this platform cannot do is predict a failure that hasn't yet produced an observable signal in logs, metrics, traces, or health checks — it's an observability platform, not a crystal ball.

**Can engineers quickly identify root causes?** The trace tree plus self-time-ranked bottleneck detection point at the actual slow span, not just the slow request; slow-query analysis groups by operation name directly from spans; the incident timeline is a complete audit trail of what happened and when; and topology's downstream-impact BFS answers "what else breaks if this fails" before an engineer has to reason it out manually from a diagram that might be out of date.

**Can telemetry scale to billions of events?** The schema and query patterns are built for it — append-only high-volume tables (logs, metric points, spans) with no soft-delete flag to maintain, bulk retention sweeps as single SQL statements rather than row-by-row deletes, and aggregation computed from indexed range queries rather than full scans. What this build has NOT done is prove that scale empirically — it runs on SQLite for development/testing, and a real billions-of-events deployment needs a genuine time-series-optimized backend (a columnar store or a purpose-built TSDB) behind the same repository interfaces, the same disclosed "swap the storage engine, keep the interface" posture every prior AIOS platform has taken for its own honestly-scoped approximations.

**Can new services integrate without redesign?** Any service that can POST logs, metrics, and spans and register a component gets health monitoring, alerting, tracing, dependency mapping, and dashboards for free — nothing in this platform hardcodes which upstream AIOS subsystem (or future one) it's observing. `NullNotificationSender` is a `Protocol`-based extension point already proven out with a working reference implementation, so wiring in real Slack/PagerDuty/email delivery is a one-class change behind an interface every escalation call site already uses.

**Can enterprises rely on this platform for mission-critical operations?** The parts that need to be correct under real concurrent load — alert deduplication — are proven correct by a real stress test, not just claimed. The parts that are honestly approximations (anomaly detection as a z-score check, capacity forecasting as linear regression, log/text search as lexical matching) are disclosed as such with a stated extension point, not silently passed off as more sophisticated than they are. The retention and audit-log machinery gives operators a real compliance story. The gap between this and a fully mission-critical deployment is infrastructure, not architecture: a real TSDB/log-index backend, horizontal scaling for the in-process alert-dedup lock (which is correct for one process and would need a distributed lock across a scaled-out fleet, the same caveat already documented for the Identity Platform's rate limiter), and a real notification-delivery integration.

## What's explicitly out of scope (per this phase's scope boundary)

No Security & Guardrails platform, no MLOps, no Deployment Platform — this is the Enterprise Monitoring, Logging & Observability Platform only, exactly as scoped.
