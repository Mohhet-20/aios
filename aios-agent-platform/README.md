# AIOS — Enterprise Multi-Agent AI Platform

Phase 6 deliverable: the intelligent orchestration layer of the AI Operating System — agent architecture, a data-driven agent-type registry, task planning, seven orchestration strategies, inter-agent communication, reasoning & reflection, tool integration, safety & governance, and observability & evaluation-lite metrics, all built on top of Phase 4's AI Core (every model call is real, routed, cost-tracked, and structured-output-validated, never stubbed). Not a chatbot collection, not an AutoGPT clone, not a LangGraph demo — a production-shaped platform for running many specialized agents against a shared task tree with real dependency ordering, real concurrency limits, and real governance gates.

## Running it

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt   # installs aios-ai-core editable from ../aios-ai-core
cp .env.example .env

uvicorn agent_platform.main:app --reload --port 8300
# http://localhost:8300/docs — OpenAPI/Swagger, 85 endpoints across 11 routers
# http://localhost:8300/health

pytest   # 136 tests, all green, zero real network calls
```

Every AI Core call in the test suite runs through a fully scripted, network-free `ScriptedProvider` double (`tests/conftest.py`) — the same pattern the AI Core project and the Prompt Platform both use — while still exercising the genuine execution/routing/structured-output/cost path.

## Architecture

**Domain model** (`agent_platform/domain/`, `agent_platform/models/`): 16 tables — workspaces, the data-driven `AgentTypeModel` registry, `AgentModel` (identity/role/capabilities/skills/goals/instructions/memory-access/tool-permissions/context-window/configuration/version/lifecycle/health/resource-limits, every field the AGENT ARCHITECTURE spec calls for), tool-permission grants, `TaskModel` (self-referential `parent_task_id`/`root_task_id`/`depth` — a goal's decomposition into subtasks *is* the task tree, not a separate "Plan" concept) plus a distinct `TaskDependencyModel` DAG-edge table, delegations, executions and checkpoints, messages and shared-workspace entries, reasoning traces and reflections, and governance (approval gates, audit log, permission grants).

**17 agent types, zero hardcoded classes**: Planner, Research, Reasoning, Critic, Reviewer, Verifier, Coding, Documentation, Summarization, Retrieval, Memory, Tool, Workflow, Reporting, Coordinator, Human Approval, and System are seeded `AgentTypeModel` rows (`agent_registry/seed_types.py`), not Python classes — adding an 18th type is one `create_type()` call, not a code change. This directly answers the spec's own self-review question about extensibility without modifying existing code.

**Agent Registry & Builder** (`agent_platform/agent_registry/`): agent creation from a type's defaults with per-instance overrides, the lifecycle state machine (DRAFT → ACTIVE ⇄ PAUSED → DEPRECATED → ARCHIVED, enforced by `domain/entities.py`'s `Agent` dataclass), health status, tool-permission grant/revoke/check, search and listing.

**Task Planning** (`agent_platform/planner/`): LLM-backed goal decomposition (`decompose_goal`, structured-output-validated against `DecompositionPlan`, reusing the Prompt Platform's repair-retry pattern) with a hard recursion-depth ceiling (`RecursionLimitExceededError`, default depth 6) checked *before* any model call; dependency-edge wiring with cycle detection (`domain/dependency_graph.py`); topological execution ordering (Kahn's algorithm, priority-tiebroken); resource estimation and progress tracking; and adaptive replanning (cancels not-yet-completed siblings, preserves completed results as context, re-decomposes).

**Orchestration** (`agent_platform/coordination/`, `agent_platform/execution/`): `AgentExecutor` is the shared "one agent turn" primitive — renders an agent's instructions + a task's goal into a model call, runs a real ReAct-style tool-calling loop when a `ToolBridgeService` is wired in, and persists an `AgentExecutionModel` row every time, success or failure. `TaskOrchestrator` builds all seven required strategies on top of it: **sequential** (topological order, dependency-success gating, stop-on-failure or continue-and-block), **parallel** (wave-based DAG scheduling, semaphore-bounded), **hierarchical** (a coordinator delegates each task to the best-fit worker via `route_task`'s load/success-rate scoring), **dynamic delegation** (`delegate()`, recorded and inspectable), **consensus** (parallel independent attempts + majority-vote by normalized response text, with a real agreement-ratio gate), **supervisor-controlled** (a supervisor agent picks the next worker each round via a structured-output `SupervisorDecision`), and **collaborative** (agents iteratively refine a shared blackboard draft). Interruptible execution (`cancel` + a per-root-task `asyncio.Event` checked at every loop boundary) and recovery after failure (`checkpoint`/`recover`, backed by `ExecutionCheckpointModel`) are both real, not stubs — these are explicitly in-scope under ORCHESTRATION even though the full Workflow Engine is not.

**Inter-Agent Communication** (`agent_platform/communication/`): direct/broadcast/status-update/handoff/event/log messages, all persisted as `MessageModel` rows and mirrored onto an in-process `EventBus` (documented as the swap point for Kafka/Redis/NATS at real scale), plus a per-task shared workspace (blackboard) key-value store used by both `CommunicationService` directly and the collaborative-execution strategy.

**Reasoning & Reflection** (`agent_platform/reasoning/`, `agent_platform/reflection/`): chain-of-thought (one structured-output call, confidence = min(self-reported, attempt-based) — deliberately conservative) and tree-of-thought (N independent branches run concurrently, highest-confidence branch wins) reasoning, persisted as `ReasoningTraceModel` rows; critique cycles, self-review/self-correction, and verification-before-final-output all built on one `CritiqueResult` structured-output contract (`ReflectionService.critique` / `.verify_output`), and a real `run_reflection_loop` that re-runs the worker agent with the prior critique injected as context until it passes or `max_iterations` is exhausted.

**Memory / Tool / Workflow bridges** (`agent_platform/agent_memory/`, `agent_platform/tool_bridge/`, `agent_platform/workflow_bridge/`): Tool integration is real — `ToolBridgeService` filters the AI Core's `ToolRegistry` against each agent's own `AgentToolPermissionModel` grants (two independent gates: the AI Core's generic `requires_permission` tag and this platform's per-agent RBAC), invokes tools sequentially (deliberately, since `AsyncSession` isn't safe for concurrent use), and bridges MCP-shaped tool specs in via `register_mcp_tool`. Memory and Workflow are, per the scope boundary, clean interfaces with one honest minimal implementation each: `MemoryService` gates every read/write against an agent's own `memory_access` flags before touching an in-process `InMemoryMemoryBackend`; `WorkflowEngine`'s reference implementation (`NotIntegratedWorkflowEngine`) raises a clear, documented error on every method rather than silently no-op-ing, pointing callers at `TaskOrchestrator.cancel/checkpoint/recover` for what's real today.

**Safety & Governance** (`agent_platform/permissions/`, `agent_platform/policies/`): RBAC with agent-scoped grants beating workspace-scoped grants (specific beats general) and an implicit OWNER role for an agent's own `owner_id`; approval gates wired as a real behavioral check inside `TaskOrchestrator._execute_task` (a non-autonomous agent or a task flagged `sensitive` in its context is routed to `WAITING_APPROVAL` instead of executing, with the approval/rejection driving the task's real lifecycle state); an append-only audit log; and `PolicyEngine` enforcing rate limits (executions-per-minute per triggering principal) and per-agent resource quotas (concurrent-execution ceilings) as hard, raised exceptions rather than advisory warnings.

**Observability & Evaluation-lite** (`agent_platform/monitoring/`, `agent_platform/analytics/`, `agent_platform/evaluation/`): unified execution timelines (executions + messages + reasoning traces + reflections, merged and time-sorted), delegation chains, agent health summaries, and p50/p95/p99 cost/latency rollups — all read directly from already-persisted rows. Evaluation-lite computes seven real metrics from that same observability data (task success rate, planning quality via cancellation ratio, a reasoning-quality confidence proxy, tool effectiveness, reliability via retry burden, collaboration quality via message/participant counts, and failure-recovery rate) — genuine arithmetic, not an LLM-judge pipeline, per the scope boundary.

**REST API** (`agent_platform/agent_api/`): 11 FastAPI routers (workspaces, agent-types, agents, planning, orchestration, communication, reasoning/reflection, tools, memory, governance, observability/evaluation) — 85 endpoints total, documenting the Frontend Experience contract (Agent Dashboard/Registry/Builder/Profiles, Execution Timeline, Task Graph, Delegation Graph, Conversation Inspector, Reasoning Viewer, Tool Activity, Health Dashboards, Approval Center) the same way Phase 5 scoped its own API-contract-not-React-code delivery. Domain exceptions map centrally to HTTP status codes so no router needs a try/except. Auth is the same intentionally minimal `X-User-Id` header seam as the Prompt Platform, actually enforced (and threaded through as `triggered_by` for execution attribution and rate limiting) on the orchestration execute-sequential/execute-parallel endpoints specifically, rather than left as an unused dependency.

## Testing

136 tests, all passing in a single combined run: 21 domain-entity tests (agent/task lifecycle state machines), 10 Agent Registry tests, 8 Planning tests, 10 Communication tests, 15 Orchestration tests (all seven strategies, cancellation, checkpoint/recovery, policy-gated approval routing, resource-quota enforcement), 8 Reasoning & Reflection tests, 9 Tool Bridge tests (permission filtering, denied/allowed invocation, the AgentExecutor tool-calling loop including round-limit and denial-recovery behavior), 5 Memory tests, 2 Workflow-bridge interface tests, 19 Governance tests (RBAC precedence, approval workflow, audit log, rate limiting, resource quotas), 8 Observability/Analytics tests, 7 Evaluation-lite tests, 2 load-shape/concurrency tests, and 15 full-stack API integration tests (real FastAPI app, ASGI transport, dependency-overridden DB session and AI Core). Zero real network calls anywhere.

The same "write real tests immediately, run them, fix genuine bugs" loop surfaced real issues: a `Capability.CHAT` enum value that doesn't exist in the AI Core (fixed the test double, not the AI Core); a naive-vs-aware datetime comparison in the execution timeline once rows started round-tripping through SQLite from different code paths (fixed by normalizing to UTC-aware before sorting, not by hoping every column stays in the identity map); a genuine concurrency bug where `asyncio.gather`-driven parallel/consensus execution branches all shared one `AsyncSession`, which isn't safe for concurrent use (`InvalidRequestError: Session is already flushing`) — fixed with a `TaskOrchestrator._session_lock` serializing session-touching work per branch, and then *tested* for what it actually does (a dedicated load-shape test proves max concurrent model calls really is 1, not just claimed in a comment); and a `ScriptedProvider` retry-masking gap where pushing a single `RuntimeError` didn't actually fail a test because `run_with_retry`'s default retry succeeded against the double's no-script fallback response (fixed the test's script, not the retry logic, since the retry behavior was correct).

## Self-review

**Can new agents be added without modifying existing agents?** Yes, and this is the platform's central design commitment. Agent types are data (`AgentTypeModel` rows via `create_type()`), not Python classes — the 17 built-in types and any custom type a workspace defines share one code path. An individual agent instance's instructions, goals, capabilities, and tool grants are all per-row overrides on top of its type's defaults, so customizing one agent never touches another's definition or any orchestration code.

**Can this scale horizontally?** The orchestration engine's stateless pieces (routing scores, DAG topological ordering, consensus voting, structured-output calls) parallelize freely across worker processes — nothing in `TaskOrchestrator` holds process-local state except the cancellation-token dict and the session lock, both explicitly scoped to one request's `RepositoryRegistry`/session. The honest constraint: this deliverable's `EventBus` is in-process pub/sub and cancellation tokens live in one orchestrator instance's memory, both documented as the exact swap points (a real message broker, a shared cache like Redis) a horizontally-scaled deployment needs — the interfaces they'd replace are already the only things any calling code touches.

**Is failure in one agent isolated from the rest of the system?** Yes, at the primitive level: `AgentExecutor.run()` never lets a model-call or tool-call exception escape uncaught — every failure becomes a recorded `AgentExecutionModel` row and a typed `ExecutionOutcome`, not a crash. At the orchestration level, `execute_sequential`'s `stop_on_failure=False` mode and `execute_parallel`'s per-task blocked/failed tracking mean one task's failure doesn't corrupt sibling tasks' state — a failed task's DB row says FAILED, not "the whole tree exploded." Consensus and collaborative strategies go further: they tolerate a minority of agents failing outright and still produce a result from the ones that didn't.

**Can workflows recover from crashes?** Task-execution-scoped recovery is real: `checkpoint()`/`recover()` persist and restore resumable state, and `recover()` correctly branches on whatever state a task crashed in (FAILED → retry, WAITING_APPROVAL → resume, BLOCKED → re-enter execution). The honest boundary: this is recovery for one task's execution, not a general-purpose durable workflow engine spanning long-running, multi-day, cross-system business processes — that's `WorkflowEngine`'s job, explicitly out of scope per the scope boundary, with `NotIntegratedWorkflowEngine` making the boundary an error message instead of a silent gap.

**Can enterprises trust autonomous agent execution?** The things a careful buyer's checklist would ask for are real, not decorative: approval gates that actually block execution (not just a database flag nobody reads — `PolicyEngine.requires_approval` + `_execute_task`'s early-return is load-bearing), rate limiting and resource quotas that raise real exceptions, an append-only audit log, RBAC with correct precedence resolution, and tool permission checks enforced twice (platform RBAC and the AI Core's own tag-based gate). The honest gap: `triggered_by`/actor attribution is wired through the two most-used orchestration endpoints (execute-sequential, execute-parallel) but not yet all seven strategies — a documented, scoped next step, not a hidden one.

**Is the platform extensible for developers?** New agent types need no code. New orchestration strategies are new `TaskOrchestrator` methods built on the same `AgentExecutor`/`_execute_task` primitive every existing strategy uses, so they inherit policy enforcement, communication logging, and lifecycle transitions for free. New tools register through the AI Core's `ToolRegistry` (first-party) or `ToolBridgeService.register_mcp_tool` (MCP-shaped specs) without `AgentExecutor`'s tool-calling loop changing at all.

**Is the platform ready for future reasoning models and agent frameworks?** Reasoning is already a swappable mode (`ReasoningMode.CHAIN_OF_THOUGHT`/`TREE_OF_THOUGHT`, dispatched by `ReasoningService.think`), and both are thin wrappers around the AI Core's `StructuredOutputEngine` — a future reasoning-native model (one that returns its own chain-of-thought natively) plugs in as a new `ai_core` capability without this platform's reasoning contract (`ReasoningTraceModel`, confidence scoring) changing. `AgentExecutor`'s tool-calling loop is a standard ReAct shape, compatible with the direction most agent frameworks and reasoning models are converging on.

## Known limitations (by design, per the Phase 6 scope boundary)

No Memory Platform (one honest in-process stub backend behind a real interface), no Workflow Engine (a documented, erroring seam, not a silent no-op), no Enterprise Evaluation platform (evaluation-lite computes real metrics from observability data, not LLM-judge scoring or golden test cases), no MLOps. "Frontend Experience" is delivered as the API/UX contract (85 REST endpoints across 11 routers) those interfaces would consume, not new React code — consistent with this project's established pattern of building actual frontend UI only in the dedicated frontend prompt.
