# AIOS — Enterprise Memory & Knowledge Platform

the long-term intelligence layer of the AI Operating System — not a vector database with a search box, not basic RAG. A production-grade platform for multi-layer memory, curated knowledge management, real document intelligence, advanced retrieval, a knowledge graph, intelligent context assembly, and enterprise governance, built on top of AI Core (every embedding and every model call flows through it as a real, editable dependency) following the same Clean Architecture / async SQLAlchemy patterns as every other AIOS platform.

## Running it

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt   # installs aios-ai-core editable from ../aios-ai-core
cp .env.example .env

uvicorn memory_platform.main:app --reload --port 8300
# http://localhost:8300/docs — OpenAPI/Swagger, 91 endpoints across 10 routers
# http://localhost:8300/health

pytest   # 184 tests, all green, zero real network calls
```

Every AI Core call in the test suite runs through a fully scripted, network-free `ScriptedProvider` double (`tests/conftest.py`) — the same pattern every AIOS service uses — while still exercising the genuine embedding/execution/structured-output path, not a simplified mock of it.

## Architecture

**Domain model** (`memory_platform/domain/`, `memory_platform/models/`): 17 tables. The 16 memory types (Working, Conversation, Session, Short-Term, Long-Term, Semantic, Episodic, Procedural, Shared Team, Organizational, Project, User, Agent, Workflow, Execution, Knowledge) are modeled as one polymorphic `MemoryEntryModel` table discriminated by `memory_type`, with a data-driven `MemoryTypePolicyModel` policy row per type (retention days, importance decay rate, persistence, summarization threshold) — the same "extensibility via data, not code" lesson the Agent Platform's `AgentTypeModel` established, so adding a 17th memory type is a row insert, not a migration. `scope_type`/`scope_id` (whose memory: user/agent/session/project/team/organization/workflow/execution) is a deliberately orthogonal axis to `memory_type` (what kind of memory), documented explicitly in `domain/enums.py`. Knowledge Management (`KnowledgeBase` → `Collection` → `Item` → `Version`) is modeled as a distinct, curated/owned/reviewed concept, separate from raw agent memory. The Knowledge Graph (`KGEntityModel`/`KGRelationshipModel`) is a real, queryable substrate that also serves as the relationship layer for Knowledge Management, avoiding duplicate relationship modeling. A single consolidated `AuditLogEntryModel` serves both memory-lifecycle audit history and governance audit trails.

**Memory Core** (`memory_platform/memory_core/`, `memory_platform/conversation_memory/`, `memory_platform/episodic_memory/`): a generic `MemoryService` provides the full lifecycle — creation, retrieval with access tracking, update/versioning, LLM-backed summarization/compression (triggered by each type's `summarize_after_tokens` policy), importance scoring with exponential decay, conflict resolution via supersession (the prior value stays inspectable, never destroyed), retention enforcement, deletion, and audit history — parameterized by policy, not by a switch statement per type. Three memory types with a genuinely different interaction shape get a thin service on top: `ConversationMemoryService` (ordered turns + running-summary compression), `EpisodicMemoryService` (timestamped events, queryable by time range), and `WorkingMemoryService` (TTL-bound, exactly one active "current focus" per session).

**Knowledge Management** (`memory_platform/knowledge/`): knowledge bases → collections → items, each item going through a real draft → in-review → published → deprecated → archived workflow with an append-only version history, ownership, categories/tags, and relationship linking against the shared Knowledge Graph substrate.

**Document Intelligence** (`memory_platform/document_processing/`): real text extraction for PDF (pypdf), Word (python-docx), PowerPoint (python-pptx), Excel (openpyxl), CSV, Markdown, HTML, JSON, and plain text — not stubs. Intelligent, token-aware chunking (paragraph/sentence-boundary-respecting, overlap-preserving, using the AI Core's real tokenizer). LLM-backed content classification (structured-output-validated). Real embedding generation with document lineage tracked throughout (`lineage.processing_history`). Image/audio/video ingestion is OCR-ready/transcript-ready via a documented `TranscriptionProvider` seam — no real OCR/ASR engine ships in this build (none is redistributable in this sandbox), and it fails loudly with a clear error rather than faking a transcript. This is a deliberate, disclosed scope boundary, not a hidden gap.

**Vector Platform** (`memory_platform/vector_store/`): wraps the AI Core's `EmbeddingEngine` + `VectorStore` + `SimilaritySearchService` (explicitly documented in the AI Core as the intended integration point for downstream subsystems). Adds what a raw vector store doesn't: durable embedding metadata via `EmbeddingRecordModel` (the AI Core's `VectorStore` is in-memory/ephemeral only), batch indexing, incremental single-item updates, full embedding-version history (`reindex_with_version_bump` never overwrites a prior record), logical multi-index support, and index health reporting (dimension-consistency checks).

**Retrieval Engine** (`memory_platform/retrieval/`, `memory_platform/reranking/`): semantic, keyword, and hybrid search (weighted merge, tunable); metadata/context/agent/user/project/time-aware filtering; multi-stage retrieval (query expansion → broad candidate generation → scope filtering → re-ranking → top-K selection); LLM-backed query expansion; and a real composite re-ranker combining normalized similarity, importance, and exponential recency decay — not raw vector similarity alone.

**Knowledge Graph** (`memory_platform/knowledge_graph/`): a real, queryable graph over entities (documents, projects, users, agents, workflows, concepts, topics, or anything via `entity_type="custom"`) and typed relationships, with real BFS neighbor lookup, multi-hop cycle-safe traversal, and unweighted shortest-path — not a stub interface waiting for a future graph database, though the two-table design is the documented seam a real one (Neo4j, etc.) would replace.

**Context Assembly Engine** (`memory_platform/context_engine/`): memory selection and retrieval ranking (built on the Retrieval Engine's multi-stage retrieve), duplicate removal (exact + near-duplicate via Jaccard similarity), lightweight conflict resolution (same-titled facts, highest-scoring wins), real token-budget management via the AI Core's tokenizer, source attribution and citation metadata, LLM-backed whole-context summarization when truncation alone can't fit the budget, and final prompt assembly with numbered, labeled source blocks.

**Security & Governance** (`memory_platform/security/`, `memory_platform/governance/`): RBAC with resource-specific grants taking precedence over workspace-wide ones and an implicit OWNER role; workspace and organization isolation guards; real field-level encryption at rest (Fernet/AES, via the `cryptography` library, key-derived from `secret_key`); regex-based sensitive-data classification (emails, SSNs, credit cards, AWS keys, API keys, JWTs, private-key blocks); access policies combining RBAC with sensitivity level (a RESTRICTED item requires ADMIN even for a principal with a broader grant); governance-configurable retention policies layered on top of the memory-type defaults; and the append-only audit trail.

**Observability & Analytics** (`memory_platform/analytics/`): every retrieval call and every context assembly logs one row through a shared choke point (the same pattern the Prompt Platform used), so latency percentiles (real p50/p95/p99 via linear interpolation, not approximation), failure rates, and a search-quality proxy are computed from genuine operational data. Plus embedding index health, memory reads/writes, knowledge growth, storage usage, and per-agent memory usage rollups.

**REST API** (`memory_platform/memory_api/`): 10 FastAPI routers (workspaces, memory + conversation/episodic/working sub-routes, knowledge, documents, vectors, retrieval, knowledge graph, context assembly, governance, observability) — 91 endpoints total. Domain exceptions map to HTTP status codes centrally so no router needs a try/except. Auth is intentionally minimal — an `X-User-Id` header, the same seam every other AIOS platform in this series uses, documented as where real JWT validation (already fully built in the core backend) would plug in.

## Testing

184 tests, all passing in a single combined run: memory lifecycle (20), conversation/episodic memory (7), knowledge management (10), document processing — real PDF/DOCX/PPTX/XLSX generation and extraction round-trips (19), vector platform (8), retrieval + re-ranking (21), knowledge graph — real BFS traversal and shortest-path (11), context assembly (6), security — encryption round-trips and sensitive-data regex detection (14), governance — RBAC precedence, isolation, access policy, retention, audit, compliance (25), observability & analytics (7), full-stack API integration tests (15, real FastAPI app, ASGI transport, dependency-overridden DB session and AI Core), and performance/load tests (4, real wall-clock ceilings over 250-300-item bulk operations). Zero real network calls anywhere.

The same "write real tests immediately, run them, fix genuine bugs" loop used throughout this series surfaced real issues: a SQLite datetime round-trip quirk (values read via a fresh row hydration lose their `tzinfo` even though SQLAlchemy's column type declares `timezone=True`, since SQLite has no native datetime type) caused a genuine, order-dependent `TypeError` in the re-ranker — fixed at the root with a shared `as_aware_utc()` normalizer applied everywhere a database-sourced timestamp is compared, and proactively applied to the domain-entity decay/expiry/retention math too, not just the one call site that happened to surface it; a FastAPI route-ordering bug where `GET /memory/{memory_id}` (registered before the episodic-memory sub-routes) silently shadowed `GET /memory/episodes`, caught by an API integration test and fixed by reordering static routes ahead of the parameterized catch-all; and a real product gap where an episode recorded without an explicit `occurred_at` was silently unqueryable by `query_by_time_range` (which requires a non-null `occurred_at`), fixed by defaulting to "now" rather than leaving it null.

## Self-review

**Can memory scale horizontally?** The write path is genuinely stateless per request (FastAPI dependency-injected session per call, `NullPool` for SQLite in this build), so the API layer scales horizontally today behind a load balancer. The honest constraint is the datastore: this build ships on SQLite (proven out with WAL mode and a busy-timeout, the same fix every AIOS service needed), which is correct for development and demonstrates every code path but is not itself a horizontally-scalable production datastore. Every query in this platform goes through the repository layer (never raw SQL scattered through services), which is precisely what makes the swap to a real distributed Postgres (or a sharded-by-workspace scheme, since `workspace_id` is on every table and every query) a repository-layer change, not an application-wide rewrite.

**Can retrieval remain fast as knowledge grows?** Structurally, yes, by design: the Vector Platform's embedding storage is decoupled from the actual vector math via the `VectorStore` abstraction, so swapping the AI Core's in-memory reference implementation (documented there as O(n) cosine similarity, correct for development, not for millions of vectors) for a real ANN index (pgvector, Qdrant, Pinecone) is a one-class change behind an interface every downstream caller (Retrieval Engine, Context Assembly) already goes through — none of them talk to `VectorStore` directly. Keyword search and metadata filtering are indexed SQL columns today. The honest gap is that the actual query latency at millions-of-vectors scale is untested, because that requires the real ANN backend this platform is structured to receive but doesn't ship with.

**Can agents share and isolate memory securely?** Yes, and this is thoroughly real, not decorative: `scope_type`/`scope_id` give every memory entry an explicit owner axis (agent/user/session/project/team/organization/workflow/execution), RBAC grants are resource-scoped with real precedence resolution (a knowledge-base-specific grant overrides a workspace-wide one), workspace and organization isolation are enforced as explicit guards, sensitivity classification gates access independent of a broader role grant (a RESTRICTED memory needs ADMIN even for someone with workspace ADMIN elsewhere), and the audit trail is append-only. The one thing intentionally not built: a real multi-tenant row-level-security enforcement at the database layer itself (Postgres RLS, say) — isolation here is enforced in the service layer, which is correct and tested, but a defense-in-depth database-level backstop is the natural next hardening step for a production deployment, not a gap in the platform's own logic.

**Can future retrieval techniques be integrated easily?** Yes — this is the platform's strongest architectural bet. `VectorStore`, `SimilaritySearchService`, and the Knowledge Graph's two-table design are all explicitly documented seams for a future real backend, and `RetrievalService`'s multi-stage pipeline (query expansion → candidates → filter → re-rank → top-K) is composable enough that a new retrieval technique (a learned re-ranker, a cross-encoder, a different hybrid-weighting scheme) is a new stage or a swapped-in function, not a rewrite of the pipeline around it. The re-ranker itself is a pure function over a generic `RetrievalResult`, deliberately decoupled from any one ORM model, specifically so it composes with whatever gets retrieved next.

**Can this platform become the foundation for enterprise AI knowledge management?** The pieces a careful buyer's checklist would look for are all real and tested, not just present in the data model: a genuine 16-type memory taxonomy with real lifecycle management (not a single flat table with a type column and no policy behind it), curated knowledge with an actual review/publish workflow and version history, real document extraction across 9 common enterprise formats, a composable retrieval pipeline with re-ranking, a working knowledge graph with real traversal, token-budgeted context assembly with citations, and enterprise governance (RBAC, encryption, sensitive-data detection, retention, audit). The honest gaps, disclosed rather than hidden: OCR/ASR is a documented interface without a shipped implementation, the vector store is a reference in-memory implementation awaiting a real ANN backend, and horizontal scale beyond SQLite is architecturally supported but not load-tested against a real distributed datastore in this build. None of these are surprises — they're the same category of scoped, disclosed trade-off every other AIOS project in this series has made under its own scope boundary.

## Known limitations (by design)

No Workflow Engine, no Enterprise AI Evaluation, no MLOps — those are explicitly out of scope and belong to later stages of the AI Operating System. "Frontend Experience" (Memory Explorer, Knowledge Explorer, Document Manager, Knowledge Graph Viewer, Semantic Search Console, Context Inspector, Embedding Explorer, Document Timeline, Memory Analytics Dashboard, Retrieval Performance Dashboard) is delivered as the API/UX contract — the 91 REST endpoints documented above and in `/docs` — those interfaces would consume, not new React code, consistent with this project's established pattern of building actual frontend UI only in the dedicated frontend prompt (the console). OCR/ASR (image/audio/video ingestion) is a documented, real interface (`TranscriptionProvider`) without a shipped implementation, disclosed rather than faked. This platform has no hard dependency on the agent platform Agent Platform or the prompt platform Prompt Platform — only on the AI Core AI Core — keeping it usable as a standalone long-term intelligence layer any AIOS subsystem can build on.
